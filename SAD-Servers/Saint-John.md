# "Saint John": what is writing to this log file?

## Scenario

A developer created a testing program that was continuously writing to the log file:

```bash
/var/log/bad.log
```

As the file continued to grow, it began consuming disk space unnecessarily.

The objective was to identify the process responsible for writing to the log file and terminate it without deleting the log file itself.

---

## Investigation

I began by inspecting the running processes on the system:

```bash
ps auxf
```

Although this displayed the process tree, there was no obvious indication of which process was writing to the log file.

Next, I attempted to identify the process using:

```bash
lsof /var/log/bad.log
```

However, the command became unresponsive, likely due to the amount of activity being generated by the file.

To confirm that the file was actively being written to, I monitored it in real time:

```bash
tail -f /var/log/bad.log
```

This showed a continuous stream of new log entries, confirming that a running process was still writing to the file.

I then used `fuser`, which is designed to identify processes currently accessing a file:

```bash
fuser -v /var/log/bad.log
```

The output revealed that process ID (PID) `7` had the file open.

---

## Solution

Once I identified the offending process, I terminated it using:

```bash
kill -9 7
```

After terminating the process, I monitored the log file again:

```bash
tail -f /var/log/bad.log
```

No new entries appeared, confirming that the process had stopped and the issue was resolved.

---

## Commands Used

```bash
ps auxf
lsof
tail
fuser
kill
```

---

## What I Learned

* How to investigate which process is interacting with a file.
* The difference between `lsof` and `fuser`.
* How to monitor log files in real time using `tail -f`.
* How to terminate a process using its PID.
* The importance of investigating the root cause rather than simply deleting a problematic file.

---

## Key Takeaway

This challenge demonstrated a common Linux troubleshooting scenario: identifying a process responsible for excessive log generation. Rather than removing the log file, I investigated the underlying cause, identified the responsible process, and terminated it safely. This reinforced the importance of process investigation and log analysis when troubleshooting Linux systems.
